# PaperKG / ScienceKG Memory

## Current State

- Phase 1 is implemented: harvester clients, deduplication, DuckDB metadata storage, and local PDF storage.
- Phase 2 is implemented as a local Kuzu-backed citation graph pipeline: metadata ingestion, citation/reference persistence, reference stub nodes, obsolescence scoring, co-citation similarity, API endpoints, and Streamlit graph visualization.
- Phase 3 is implemented as the extraction layer: LLM router, PDF parser routing, ontology-aware entity extraction, canonical entity linking, vocabulary/review management, embeddings, conflict detection, batch processing, FastAPI endpoints, and Streamlit UI. The current extraction direction is precision-first: uncertain/high-recall entities are candidates or review items, not automatic KG nodes.
- Phase 4 is implemented as a first local query-assistant layer: deterministic KG retrieval, hybrid retrieval with stored entity embeddings, grounded responses, hypothesis generation, FastAPI endpoints, Streamlit chat/detail/project UIs, source/PDF verification, and a one-command runner.
- Phase 5 is started but not production-complete: extraction benchmark tooling exists, Phase 4 answer evaluation exists, KG health reporting is implemented, and maintenance/automation modules are still partial or placeholders.

## Architecture Notes

- `storage/metadata_db.py` is the DuckDB metadata contract for Phase 1/2/3 and the product frontend. It persists paper metadata, references/citations, extraction history, persistent project notes, note citations/assets, note AI threads, note versions, and resettable local state.
- `api/main.py` serves Phase 2 graph endpoints. `POST /graph/phase2/build` writes Paper, CITES, and co-citation SIMILAR_TO edges.
- `graph/paper_ingestion.py` normalizes Paper nodes and citation IDs from metadata records.
- `graph/paper_ingestion.py` also ingests successful extraction rows into semantic `Concept`, `Method`, `HAS_CONCEPT`, and `HAS_METHOD` graph records when graph builds include extractions.
- `graph/kuzu_schema.py` owns the Kuzu schema and graph writes, including Paper/Citation writes and semantic Concept/Method edge writes.
- `api/phase3_main.py` serves Phase 3 extraction endpoints and persists API batch extraction results to DuckDB.
- `ui/graph_visualization.py` is the Phase 2 graph UI.
- `ui/phase3_extraction.py` is the Phase 3 extraction UI with PDF Library, Extract, Batch, Harvest, History, and Vocabulary tabs.
- `api/phase4_main.py` serves Phase 4/early Phase 5 frontend-facing endpoints: `/query/search`, `/query/answer`, `/query/hypotheses`, `/sources/verify-answer`, `/paper/pdf`, `/papers/{paper_id}`, `/papers/{paper_id}/neighborhood`, `/system/health-report`, and `/quality/benchmark`.
- `query/kg_retriever.py`, `query/hybrid_retriever.py`, `query/grounded_responder.py`, and `query/hypothesis_generator.py` implement local grounded retrieval and answer generation over DuckDB extraction history, optional Kuzu Cypher, and stored entity embeddings.
- `query/source_verifier.py` owns reusable source verification for later custom frontends: local PDF lookup, reference text construction, extracted-PDF excerpt matching, and answer-source verification payloads. Streamlit should remain a dev workbench and consume this module instead of owning product logic.
- `quality/kg_health.py` reports Phase 5 KG health metrics across metadata, local PDF coverage, extraction status, review queue, embeddings, batch jobs, and extraction quality telemetry. It is exposed by `GET /system/health-report` and can be run with `python -m quality.kg_health`.
- `maintenance/embedding_reindex.py` now rebuilds stored entity embeddings from extraction history/review items with the offline hash-fallback backend by default. `maintenance/health_repair.py` initializes graph storage fallback state and reruns the embedding reindex; the product API exposes this via `POST /jobs/health-repair`.
- `quality/phase4_eval.py` and `quality/phase4_questions.json` provide a small grounded-answer eval set for provider comparisons. Latest local Qwen/Lm Studio report reached 8/8 after retrieval and scoring hardening; Gemini comparison can be affected by hosted 503/high-demand failures.
- `ui/chat_interface.py`, `ui/paper_detail.py`, and `ui/project_manager.py` are the Phase 4 Streamlit entry points. `scripts/run_phase4.py` starts the Phase 4 API and selected UI.
- `query/llm_router.py` supports Ollama, LM Studio, OpenAI, and generic OpenAI-compatible providers via `config.yaml`.
- Future custom frontend scope to preserve: Library Dashboard, Harvest/Import, Search, Assistant, Source Verifier, Paper Detail, Paper Network/Graph Explorer, Hypotheses, Review Queue, Extraction Workflow, Quality Dashboard, Jobs/Automation, and Settings. Streamlit is only the dev workbench; the product frontend should consume reusable FastAPI/backend modules rather than porting Streamlit layout code.
- Frontend-relevant backend gaps still to build: Review Queue merge/alias workflows, production Retraction Checker, Obsolescence Updater, KG Vacuum, robust graph explorer API/view model, global/full-text note search, and true PDF page-coordinate anchoring beyond text-item highlighting.
